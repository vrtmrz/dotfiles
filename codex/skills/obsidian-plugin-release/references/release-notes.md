# Obsidian release notes

- For vrtmrz Obsidian plug-in releases, use this order: `## <version>`, an ordinal date such as `10th July, 2026`, a brief personal note, then categorised changes.
- Obtain the personal note from the maintainer or explicitly omit it. Do not invent it. Translate a supplied Japanese note into natural British English while preserving its tone and meaning.
- For review-only refactoring pre-releases, state that the work improves robustness and maintainability, is under review through CI and a real Obsidian instance, offers no particular user benefit, and may be skipped.
- Write self-review commitments in the first person rather than addressing the maintainer with `Please`.
- Keep task boxes in release notes as guidance, and duplicate the actionable checklist in the relevant pull request body for clickable progress tracking.
- Do not replace the latest stable release when publishing a pre-release.
